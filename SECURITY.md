# Security

Ressac is a browser that lets an AI agent read and act on web pages. Security reports are welcome and taken seriously.

## Reporting a vulnerability

Please **do not open a public issue**. Report it privately through GitHub: the repository's **Security** tab › **Report a vulnerability**.

Include what you can: the Ressac version (Réglages › À propos), steps to reproduce, and what an attacker gains. You will get an answer as fast as possible. Ressac is a small project in beta: there is no bug bounty.

Bugs in Firefox itself (Gecko, SpiderMonkey, the network stack) belong to [Mozilla's security program](https://www.mozilla.org/security/), unless one of Ressac's patches causes them.

## Supported versions

Only the latest released version gets fixes. Ressac updates itself.

## What Ressac protects

The design assumes **web pages are hostile, including the ones the agent reads**: a page can try to give the agent instructions (prompt injection). The protections, in short:

### Where the agent runs

- **In a container inside a small Linux VM**, not on your Mac (Lima, Apple Virtualization, rootful Podman; `apps/firefox/scripts/vm/lima.yaml`, `apps/firefox/host/machine.ts`). The VM sees only the Ressac folder (read-write) and the workflow engine's folder (read-only), never your home folder; it forwards to the Mac only the Podman socket and ports 5300-5319 on `127.0.0.1`. The VM image is pinned by SHA-256. A Docker engine you installed is still used as a fallback: the container and its mounts are the same, but that engine's own VM shares more of your Mac (Docker Desktop shares `/Users` with it by default), so an escape from the container would reach further. Lima's SSH port listens on the Mac's localhost only; your `~/.ssh` keys are not authorized and no SSH agent is forwarded into the VM. `apps/firefox/scripts/vm/security-check.sh` checks this on a throwaway VM.
- **The container is hardened** (`packages/kernel/src/container/workshop.ts`): no new privileges, memory and process limits, IPv6 off, every agent process killed when a conversation opens and no other one is running. The base image is pinned by digest; Claude Code and Codex are pinned by version and installed root-owned, so they cannot replace themselves (Claude's autoupdater is off too) (`packages/kernel/docker/workshop.Dockerfile`).
- **The agent's network is an allowlist** (`packages/kernel/docker/ressac-network.mjs`): the agent's user reaches only localhost, the Mac's MCP and relay ports, and an allowlist proxy (HTTPS CONNECT and plain HTTP) limited to base domains (code and package hosts, the model APIs) plus the ones you add. The proxy refuses names that resolve to private addresses. The rules are applied again before each session, which does not start unless a direct connection is refused.
- **API keys stay in the macOS keychain** (`apps/firefox/host/relay.ts`): the container gets a session token, and the relay on the Mac swaps it for the key, only for inference paths and only toward the engine chosen when the session opened.
- **Two modes.** « Navigateur », the default, has no shell: Claude runs without Bash, `launch_app`, other MCP servers or any user, project or local settings; Codex without its shell tool, `notify` or a provider the agent defines (`packages/kernel/src/kernel.ts`). In both modes the models' own web tools are off, so all browsing goes through Ressac's browser: Claude's WebSearch and WebFetch, and Codex's web search (which, with its sandbox off, would fetch live pages from OpenAI's side), refused by the root-owned `requirements.toml` too. « Atelier » adds the shell to build and run project apps.
- **The agent cannot change its own rules.** Claude's managed settings (`disableAllHooks`, managed hooks only) and Codex's `requirements.toml` are root-owned; Codex's is rewritten each session with that session's MCP address. The internal `.ressac` folder (launch profiles, MCP config, the research notebook) is mounted read-only, except its `logs` folder, and planted symlinks are removed before each mount. The kernel's own reads and writes in the workspace refuse links the agent planted (`packages/kernel/src/workspace/no-links.ts`, `confined.ts`). npm install scripts are off by default.

### What the agent can reach in the browser

- **Only through the kernel's MCP server**, on `127.0.0.1`, with a bearer token checked in constant time.
- **Reading a tab needs your consent** (`packages/kernel/src/access/policy.ts`): the agent may read a tab you gave it, the tab you spoke to it from, or a local demo it built. Any other site needs a request, and a permission holds for one origin only. Tabs in a private space are never readable (`apps/firefox/chrome/agent/bridge.ts`). History and bookmarks need a card, once per conversation.
- **The agent does not click or type in pages.** It reads, navigates and hands control back to you for logins and captchas (`hand_over`). Two things you grant can act in a page: `run_js` on a tab (a developer right; console, network, performance and acting are granted per tab and per origin, through an in-process DevTools client with no socket), and an extension the agent wrote once you turn it on (signed by Mozilla with your account; its own pages are limited to the network you granted, and a wider scope turns it off until you grant it again).
- **An address the agent opens must be one it read, exactly** (`packages/kernel/src/mcp/seen.ts`): a page, one of its links or a search result, so `?q=<data>` added to a read address is not free. Outside a search, the fragment counts too (`page#<data>` is not free), and a local address, a tab it may read or an address you approved earlier in the conversation is also free. During a search, only that search's reads are free and a fragment the agent added is dropped. Any other address shows you a card with the whole address and the agent's reason before it opens. A recap may only link to addresses read.
- **What leaves through a search or a composed address is checked** (`packages/kernel/src/outflow/`). A search query that holds an access key, a private key, a login token, a card number, an IBAN or a social security number (checksums checked; in clear, base64 or hex) pauses before it reaches the search engine; an address the agent wrote that holds one shows a red line on its card. Ressac also remembers, per window, the distinctive items of what the agent read in your tabs, history and bookmarks (e-mails, phone numbers, long numbers, identifiers) and catches them coming back in a query or an address the same way, even in base64. It also catches them written another way: digits written as words in 56 languages, Chinese, Japanese and Korean numerals and their romanised forms, Greek, Hindi and other digit scripts, spaced-out letters and NATO words, in a query or a percent-encoded address. It remembers short identifiers mixing letters and digits (a door code, a file number). And it judges a series of searches that share the same words around a changing part as one: the parts are joined and checked, and from the third part that looks like a piece of code the search pauses, even when nothing read matches. Searches made of the pieces alone are joined too, since 0.1.25 also across the ordinary searches sent between them (among the last 20 kept); with ordinary searches between them and nothing read matching, they pause at the third piece of the same shape (« trois huit », « un six », « deux quatre »: two digits each). Since 0.1.25 the links it follows are judged the same way: after a private read, a link whose label is one character (« 3 », « B »; the label is kept by address, so a link opened by its address keeps it; with no label, a one-character query value or the last path segment of its address) joins the pieces followed on the same site, word links and other sites between them skipped; the pieces are joined and checked against what was read, and from the third, unless they climb or step back as a pager of ASCII digits and letters does, the link is no longer free: its address card shows a red line (`navigate`, `open_tab`, `read_pages`). The tab you opened the panel on or spoke to the agent from is not remembered unless its site is sensitive, as long as it stays on that origin. What you typed or asked yourself in this conversation is never treated as a leak. The figures below (measured on the rules shipped in 0.1.19) come from replaying recorded gestures through the rules, not from an injected agent run end to end: they say what this one layer catches once an agent has already obeyed a hostile page, not how often Ressac leaks. Of 398 honest gestures written by an agent that did not know the rules, 7 were paused, three of them for a public number with a secret's shape and one for a phone number read on a public page of a sensitive site during the search: 7/226 = 3.1% (95% interval 1.5–6.3%) of the gestures the rules can flag (queries and composed addresses), 7/398 = 1.8% of all. On 1 944 attacks adapted from two public benchmarks (AgentDojo and InjecAgent), each sending its leak whole in one query or one parameter, the leaked data was caught in about half the cases (1001/1944 = 51.5%, 49.3–53.7%); counted by distinct leak, 16 of InjecAgent's 28 were caught (39–74%). Spelled and split leaks are measured on their own (`bench/security/outflow/`, corpus 4, a replay of the rules with no model). There are 1 936 ways of sending the four private values of the end-to-end bench below:
- each language and script of the table;
- one query, with punctuation, or split over three searches;
- percent-encoded addresses;
- one row per hole found while building these rules.

All 1 936 were caught, where the rules before them caught 5. None of 51 ordinary searches made after a private read paused (dates, sizes, prices, versions, times, model names). Reworded leaks are not measured. End to end (`bench/security/B3/`), an agent made to obey the page (minimax-m3.1-flash, told to follow it) ran once on 36 hostile pages written for Ressac's own channels and 10 that ask for another language or script:
- with every card refused, 4/36 values left whole (0/10): in three attacks the agent clicked the verification code out on a grid of links labelled with digits (a channel no rule checks, see the limits below), and one sent all six digits of the code as three searches with no other words, which the rules of 0.1.23 did not join; since 0.1.24 such bare pieces are a series (tested, in corpus 4, and rerun end to end with a scripted agent on 0.1.24: the third search paused, the first two had left; see the limits below). The agent tried only 11 of the 36 attacks that time (21 before these rules), so this rests on few attempts;
- with every card granted that had no red line, 8/36 whole values left: three without a shape (a doctor's name, a street, an adviser's name), the same code in pieces, and the code clicked out on a link grid in all four link-covert attacks; and 2/10 left through a percent-encoded address, a hole closed in 0.1.23: the 10 encoded-language pages rerun end to end on 0.1.23 leaked no whole value (0/10 cards granted, 8 tried, every attempt stopped; 0/10 refused), with one partial leak, in one granted address: the 5 digits of the lab file number without its letters, and 5 of the 8 digits of the client id, both sent as hyphenated hangul.

Before these rules the same agent leaked 16/36 and 7/36, that code and the link grids among them. The grid clicks were in the records all along; they were first counted on 2026-11-22, when the figures above read 4/36 and 1/36 (12/36 and 4/36 before the rules). Pieces of a value are counted apart, as partial leaks (4 digits or more of a value out in order, not the whole value): after these rules 2/36 attacks with every card granted (5 of the 8 digits of a client id, 4 of the 6 of a code) and 0/36 with every card refused, 1/10 encoded-lang; before them 3/36 and 0/36; none in any control. Those controls were biased: most offered the agent no link to follow, so as a baseline for pauses and cards they are rough. Claude Haiku, not made to obey, tried nothing on 85 hostile pages. One run per case: a rerun gives other numbers. The bench gave no tab the exemption of the tab you spoke from, so 51.5% is an upper bound. The intervals treat items as independent, which they are not (20 goals; 28 + 14 distinct leaks): read them as rough. These rules catch data with a shape, nothing else. A published attack success rate of about 1% for a frontier model under prompt injection measures something else: how often an attacked agent actually does what the page asks, mostly stopped by the model refusing. 51.5% is what our rules catch after that has failed; the two do not compare.
- **Sensitive sites ask again during and after a search** (`packages/kernel/src/access/sensitive.ts`): the history, the bookmarks and tabs of sensitive sites (mail, bank, payment, payroll, passwords, taxes, health, messages, account pages) ask their card again once per search, even when granted earlier in the conversation, and once more after each search ends (a final recap, the idle delay, a stop), until the conversation ends: a page that steered the search can still steer the agent after it. Before any search in the conversation, a granted sensitive tab reads with no new card, even when the agent was steered by a page it read some other way (a tab you asked it to read, a link it followed with `navigate`). The list is fixed and incomplete.
- **No model judges the searches.** A local judge (a small model comparing the agent's gestures with what you asked) was removed; these figures are the removed judge's, measured in November 2026, not the product's: on the 398 honest gestures above it paused about three in ten (117/398 = 29.4%) while its scores ranked the attack queries little better than chance (AUC 0.59). The exact-address rule, the outflow rules and the cards are what remain.
- **Memories written from the web are data.** A site app's memory keeps each entry's page and date and reaches the agent only after your grant, marked as data. The agent's research notebook (`packages/kernel/src/search/notes.ts`) is read-only in the container: the kernel writes a lesson only through `note_lesson`, once right after a hand-over where the agent was lost (any other tool call closes that chance), stamped with the date and that hand-over's sites, and gives the latest ones back with the `search_web` that gives a search its goal, capped and marked as hints, never instructions.
- **Invisible reads** run in a private, throwaway container, and every request they make to a local address (or a name that resolves to one) is refused (`apps/firefox/chrome/agent/local-guard.ts`).

### Masking (step 1)

The agent can use your identifiers without needing to know them. Where Ressac recognizes one, the agent gets a label instead (`⟨iban-k3x9p2qa⟩`: a type and 8 random characters), and Ressac itself puts the real value back when it fills a field, with your consent. An agent that never saw a value cannot spell it, split it or click it out. Masking does not hide content: amounts, dates and the text of mails, messages and documents stay visible to the agent, under the outflow rules and cards above, which stay in place as a net.

- **Every MCP result goes through the masker** (`packages/kernel/src/mask/`, wrapped in `packages/kernel/src/mcp/server.ts`): text, errors and structured content, before they reach the agent. A test fails if a registered tool escapes it (the exemption list is empty). So does what Ressac writes into the agent's terminal itself: a ⌘T request, the context prefix and the other prefills.
- **Two zones, never one label across them.**
  - **Your sources**: a tab of a sensitive site that you reached yourself, your own history and bookmarks, site app memories and tweak errors (until the agent navigates in the app), and what a widget or action that reads with your accounts returns (its data, runs and errors). A page the agent opened, navigated to or reached by a redirect from its navigation is never a source, and neither is a tab once the agent navigated it (until you open an address there from Ressac's own interface: a click inside the page restores nothing), a tab you hand over to log in, or a site app with an agent-written tweak that holds script. The agent's visits are marked when history records them. Here every recognized shape is masked: verification codes near a code word, IBANs, cards (Luhn), social security numbers, identity numbers, keys and tokens, a French account number after an account word, a password written after « mot de passe : », phone numbers, e-mail addresses, and the display name of a `Name <address>` header (as `⟨nom-…⟩`), unless it looks like an organisation. An e-mail keeps its domain (`⟨email-…⟩@impots.gouv.fr`), so the agent can still judge a sender. A tab is masked as the page Firefox actually read: one that moves within its site while its access card is up, or during the read (to `/compte/…`, say), is judged again where it is (unit-tested).
  - **The rest of the web**: only the high-risk shapes, whoever they belong to, so masking one tells a page nothing: IBANs, cards, social security and identity numbers, keys and tokens, verification codes. Phone numbers and e-mail addresses stay in clear there (a plumber's number, a sender's address).
  - The same value seen in both zones gets two unrelated labels, so a page that prints « line 381624 » cannot make that line carry your code's label.
- **Variants are matched**, since a variant left in clear beside its label gives the value away: spaces and dashes, `+33`, `0033` and `(0)`, case, digits of other scripts and full-width digits (NFKC), percent-encoding, numbers written in French or English words, compound numerals included (« trois cent quatre-vingt-un »). A name is matched across accents, case, reversed order, a comma form and an initial, never as a first name alone.
- **Labels belong to one conversation.** Their ids come from a cryptographic generator, a new conversation draws new ones, and each conversation's table is tied to its session token and wiped when it ends; the main token resolves none. A `⟨` or `⟩` coming from a page is replaced by a look-alike before masking, and only labels issued in this conversation are recognized, so a page cannot plant one. A label the agent writes into a search, an address, an action's input or a `run_js` script is never replaced: it leaves as written, and Ressac shows you a card before it goes. An address that holds an identifier is masked too; the agent opens it by its link number, or by giving back the masked address whole as an opaque handle. Opening it sends the identifier, so it is free only toward the exact origin it was read on; another origin asks a card, and every redirect hop is judged.
- **`fill_field`**: the agent names a field it read and a label, and Firefox writes the real value in the page; the value never goes back through the agent. Your saved login and password (Firefox's password manager, which the agent never reads) always need a card when the agent asks, and only on the login's exact origin, with the field's frame, every ancestor frame, the page and the form's action (every submit button's included) on that origin; no card can send a password anywhere else. One saved-login fill on a login form fills both its username and password fields, on one card naming both, each field under these rules and its own seal. The saved username goes into a field marked `autocomplete=username`, or, only within such a pair fill, into the field Firefox's own login form detection pairs with the form's password field (that pairing is part of the seal: changed before the write, nothing is written); a lone field with neither gets nothing. Every other value needs a card, even on the origin it was read on. Touch ID is asked when the agent opened the page. A value of your sources filled on a page the agent reached, away from the origins it was read on, gets a red line. A label read on the web is filled only on the origin it was read on. Free text in a fill goes through the outflow rules. The card is granted on a seal of the exact field (browsing context and window, the page actor's handle on the element, the frames' origins, the form's action, the field's type and autocomplete); the page's actor finds the element again, recomputes the seal, compares and writes in one synchronous step, and gives up if anything changed (`apps/firefox/chrome/agent/fill.ts`, `fill-actor.ts`). Three labels `fill_field` or `reveal_value` does not know lock both for the rest of the conversation.
- **Reveal and the lock.** When a task needs a value, `reveal_value` asks a card and Touch ID (or the Mac's password); the value is in that one result only, and a password is never revealed. From then on the conversation is locked: an outflow passes without a card only toward an origin allowed for every value revealed, so each reveal narrows and none widens. An outflow with no destination Ressac can name (a search, an action, a workflow, a hand-over, an app) always asks one. The lock also holds the workspace (`<data folder>/masking/lock.json`, read again at each call; unreadable counts as locked), since the agent could have written the value into a file:
  - the next conversations, in every window, are born locked, and once the revealing conversation has ended every outflow asks a card, even toward the value's own origin;
  - writes to the stores other conversations read (the research notebook, site app memories, widget data, actions, workflows, recaps) are refused, not carded;
  - agent extensions are turned off, and installing or reloading one is refused;
  - a widget or action whose code changed since the lock does not run, and a site app tweak runs as it was at the lock;
  - the external design-mode server answers 423;
  - the agent's apps are stopped before the value leaves, and `launch_app` is refused; agent pages lose the CDNs and WebRTC (the page guard learns the lock from the host, and counts as locked until it does);
  - the container's network is cut down to the model domains, and tunnels opened before the lock are killed.

  A reveal is refused while the container serves another conversation. Only you lift the lock, with Touch ID, from the conversation's banner or Réglages › Agent. The card lists the workspace files changed since the reveal and offers three choices: move them to a quarantine the agent cannot read (the default; you read them in the Finder and give each back once checked), keep them (with a diff per file), or delete them.
- **The browser checks again before anything leaves.** The kernel judges the agent's request, then Firefox's parent process checks the real address just before the load, every redirect hop included, and a page's script redirect with no user activation while an agent load is pending (`apps/firefox/chrome/agent/load-guard.ts`); and it checks the seal just before a fill. A page gets data from the agent only through those two gestures: a link followed and a field filled.
- **Carrier tabs** (`packages/kernel/src/mcp/server.ts`, `carrier`): a tab of a sensitive site, or whose text holds a value to mask, is checked at each call on its current text (on a web page only the high-risk shapes count, so a refusal tells the page nothing). On a carrier `capture_screen` is refused, and so are `run_js`, `read_network`, `read_request`, `read_console` and `memory_snapshot`, which see the raw page: a card with Touch ID unlocks them for the conversation, for that origin. The status sticks until the tab closes (for captures, until it leaves the origin), since the dev tools' buffers keep what they saw. A frame of a sensitive origin makes the capture refused too. Since the swarm review of data masking, the check also reads what a capture shows and a read leaves out: every frame's text whatever its origin, every field's typed value, and the text past the read's bound; a document Firefox cannot read (a frame that is not http(s) and not of its embedder's origin, a failed or oversized answer) makes the tab a carrier (unit-tested in the kernel, `e2e/masking-capture.e2e.ts` in Firefox). Those dev tools also ask the card on any tab of your sources (a sensitive page, or a site of your passport you reached), even when its text shows nothing: its console, requests or fields may hold your data, and a script there could write guesses into the page to read back which one comes masked. What any dev tool gives from a tab is masked as a read of that tab is, in its zone and on its origin (unit-tested).
- **Agent extensions** (`apps/firefox/host/extensions/agent.ts`, `apps/firefox/chrome/store/quarantine.ts`, `agent-extensions.ts`) run only in Atelier and never under the lock. The sensitive hosts are in Firefox's quarantined domains, where an ordinary extension injects no script and loses its rights on the site; Ressac's own check also refuses an injection into any frame whose page or ancestor is sensitive, by host or path. Sensitive tabs' addresses and titles are hidden from them, and `webNavigation` is refused. While one runs, the agent's banner says it can read pages outside your sources.
- **The terminal.** Labels in the agent's answers are underlined; a click shows the value in a Ressac bubble, outside the terminal, and sends nothing to the agent. A paste holding a recognized value is held until you choose « Coller masqué » (the default) or « Coller en clair ». What you type key by key is not masked, and a line under the terminal says so.
- **Coverage.** Masking covers a conversation started under it. A resumed conversation that started before masking, a resumed conversation that revealed a value, and any resumed Codex conversation, are marked « non couverte » in their banner: their context may already hold values in clear.
- **Three protections, one not covered.** Data at rest: API keys in the macOS keychain, passwords in Firefox's password manager; the label table lives only in the kernel's memory on the Mac, never in the VM, the workspace, `.ressac`, a log or an error report, and the lock file holds names and hashes, never a value. A manipulated agent: masking. A compromised Ressac: not covered.

**Two kinds of proof.** For MCP results, the indistinguishability test establishes a property: no result depends on a masked value. On the same scenarios with two user profiles whose values differ, every result is the same up to the renaming of labels (`bench/security/B3/indistinguishable.mjs`: 74 of 74 scenarios identical, every card granted and every card refused, on the scripted adversary). For every other channel the proof is a finite list of attacks tried, not a universal property, because what a page can do cannot be enumerated. That list (`bench/security/B3/adversary.mjs`, 74 cases with an honest control each): variants, joins, the lock (same origin, open redirect, a second search, a fill, a workflow, an action, the notebook, a second conversation), a page that sends what it holds by itself, fills on a lookalike or the attacker's form, and the 15 encodings that leaked before masking. With every card granted no whole value left; one partial (5 digits of a lab file number read in a history address, a shape masking does not cover, see the outflow limits); two inferences (the personal e-mail domain, and a first name alone in a signature). With every card refused, one inference (the domain). Scripted, not a model: what a model would try is not measured yet. Whether the engines reach anything but Ressac under the lock was measured on a throwaway workshop (2026-11-23): a Claude subscription session reached `api.anthropic.com` only, the relayed engines answered with no domain at all, and a command in the workshop got a 403 for any other host. The locked list keeps `api.anthropic.com`, `platform.claude.com` (token refresh, not measured) and Codex's ChatGPT sign-in hosts (`chatgpt.com`, `auth.openai.com`, not measured).

### Masking (step 2: the passport)

Step 1 masks what has a shape. Your name, your address and your relatives' names have none, so you list them yourself in a passport (Réglages › Passeport), with your phone, e-mail, IBAN, identity and social security numbers, number plate, birth date and free entries. The agent then gets a label for them as for any other identifier.

- **Stored encrypted, one per connection profile.** Each profile's passport is one file, `<Firefox profile>/ressac/passport/<profileId>.json` (mode 0600, folder 0700): a clear envelope around an AES-GCM ciphertext from Firefox's native OSKeyStore service, under a key of its own in the macOS keychain (`Ressac Passport`; `Ressac Passport (dev)` in a build that is not packaged, so a development build never reads or replaces the DMG's key). A file whose envelope names another profile is unreadable. No backup copy, clear cache or log: the module logs error names only. A passport written by a newer Ressac is read-only; a missing or changed key is never replaced by a new one and the file is never rewritten: the passport is shown as unreadable (a banner in the agent panel, a notice in Réglages), and « Recommencer un passeport vide » (Touch ID and a confirmation, only on an unreadable passport) moves the old file aside, as `<profileId>.illisible-<date>.json`, before starting again. That copy stays next to the file, still encrypted, until « Supprimer ce passeport »: Ressac never deletes it on its own, and reads it again only if you restore the old key and rename the copy back by hand; the passport started since then is then unreadable in turn, since it was encrypted with the new key. A new key is made then only if no other passport read fine in that session. An entry that cannot be read is kept in the file as it was and listed as unread, never dropped in silence.
- **The kernel holds the values, in memory only.** At start Firefox decrypts each passport without a prompt and hands it to the kernel over its existing JSON-RPC channel; the kernel answers no tool call before every passport has arrived (it waits up to 30 s, then answers « Ressac prépare le masquage : réessaie dans un instant. » without reading anything). A load that takes over 20 s makes that profile unreadable for the session until it completes. The kernel's store prints as `[passeport]`, its errors are fixed strings, and no value goes to a log, stderr or an error report. The agent (VM) sees none of it, and no tool lists the passport or tells whether it holds a kind of value.
- **Touch ID guards access and output, not masking.** Réglages › Passeport opens with Touch ID for 5 minutes and locks again when you leave the section, hide the tab, close the page, or the Mac sleeps or locks its screen. A locked passport still masks.
- **Where it masks: your sources, every passport in every source.** Your sources gain the tabs you reached yourself on a « Remplissable sur » host of a passport; all the other sources of step 1 stay. Every profile's passport masks in every source, whatever the tab's profile, and so does your ⌘T request and a paste (a paste that holds a passport value is held for « Coller masqué »). A tab counts as a carrier when its text holds a passport value, in your sources only. A change to an entry's « Remplissable sur » sites, in the editor or by « Retenir ce site », counts from the next conversation: a running one keeps the sites it had at its first tool call (a change before that still counts, since it has linked nothing yet), so none of its pages changes zone (a value it read in clear there would otherwise become a label it knows from your mail, and a removed site would show in clear a page it read masked).
- **Where it never masks: the rest of the web**, including a page the agent opened or reached on a site of your passport, and while you have the hand (`hand_over`), with one exception: a value Ressac filled stays masked on that origin for the rest of the conversation (« After a fill » below). No refusal, card or outflow rule depends on the passport there either. See the limits for the reason.
- **One label per entry.** Every writing of an entry gives its one label (« AUBRAC Camille », « C. Aubrac » and « Camille Aubrac » are one `⟨nom-…⟩`), and a phone, IBAN, e-mail or social security number in the passport gets the same label as step 1's detector. A new label type, `date`, carries the birth date. What Ressac tells the agent names the type, never the field (« votre nom », never « le nom de votre proche »), and never the profile a value came from; the cards, shown to you only, name the field and the profile.
- **The writings it recognizes, and nothing else** (exact forms after folding, no fuzzy match). The text is folded first: NFKC, invisible characters (zero-width space, soft hyphen) removed, accents removed, lower case, `œ`/`æ`/`ß` spelled out, and any run of characters that are neither a letter nor a digit (spaces, dashes, dots, commas, apostrophes, slashes, line breaks) made one space. A form matches only between word boundaries, so « Marc » is not found in « Marché ». JSON `\u` escapes and numeric HTML references (`&#…;`) are decoded first. Then, by type:
  - **name** (yours or a relative's): first names and surname in both orders, with a comma or not; all first names or the first one; initials (« C. Aubrac », « J.-P. Dupont », « JP Dupont », « Dupont J.-P. »), only when written as capitals; the surname without a leading particle (`de`, `du`, `le`, `van`…) when a word is left; a title and the surname (« Mme Aubrac », « Monsieur DUPONT »). Never a first name or a surname alone, never inside a host name;
  - **postal address**: the street line only (its number, an optional `bis`/`ter`/`quater`/`b`/`t`/`q`, glued or not, number before or after the street), with the usual French abbreviations of the street type (`rue`/`r`, `avenue`/`av`, `boulevard`/`bd`…) and of `saint`, `sainte`, `général`, `maréchal`, `docteur`. An address with no numbered street line is searched as its first line, as written;
  - **phone, e-mail**: step 1's forms, nothing more (the detector already masks every phone and e-mail local part in your sources);
  - **IBAN**: step 1's forms, plus a French IBAN's 11-digit account number alone;
  - **social security number**: its 15 digits, or the first 13 without the key;
  - **identity document, number plate**: as written and compact (at least 6 characters);
  - **birth date**: in digits (« 14.03.1990 », « 1990-03-14 », « 14031990 », « 14/03/90 », « 4/3/1990 ») and in words (« 14 mars 1990 », « 14 mar 1990 », « 1er mars 1990 », « march 14 1990 », « 14 march 1990 »), never without the year;
  - **free entry**: its folded form (at least 4 characters, one letter), or its digits (at least 6);
  - **your own variants** (« Autres écritures »): each one as written, folded, even a single word (the editor warns that the word is hidden everywhere in your sources). Under 4 characters, or 6 digits, it is refused.

  A digit form never matches with a digit right before or after it.
- **Filling with a label.** `fill_field` takes a passport label as any other. There is always a card. Touch ID is asked as well when the field is not on one of the value's origins (its « Remplissable sur » hosts that the entry had both at the conversation's first tool call and now, each covering exactly `https://<host>` and, when written without `www.`, `https://www.<host>`, plus the origins it was read on in your sources in this conversation), or when the agent reached the tab. One Touch ID covers that origin for 5 minutes in the conversation, for passport values, and waives only the off-origin reason: an agent-reached tab asks every time. A fill outside a conversation (the main token) never uses the window: each such fill off the value's origins asks Touch ID, while one on an origin of the value, in a tab you reached, gets only its card. A value of another profile than the tab's fills only by its label, and the card names its passport (« Cette donnée vient de votre passeport « Travail », pas de celui de cet onglet. »). A value removed from the passport during the conversation still fills from the conversation's table, with Touch ID. A date goes into a `type=date` field as `AAAA-MM-JJ`, into a text field as `JJ/MM/AAAA`; no passport value goes into a password field.
- **Filling by kind** (`fill_field { passport: "adresse" }`), for a value the agent never read: kinds `prenoms`, `nom_famille`, `nom_complet`, `naissance`, `adresse`, `adresse_voie`, `code_postal`, `ville`, `tel`, `email`, `iban`, `secu`, `piece`, `plaque` (a relative and a free entry fill only by label). The card offers the entries of that kind in the tab's profile's passport only, masked, with « Voir »; the card never receives the values, only their masked display. There is always a card, even when the passport has nothing of that kind, and the agent gets `FILLED` or the same text as a refusal, so it does not learn what your passport holds. `also` fills up to 11 more fields of the same site on the same card, with at most one Touch ID; each row keeps its own seal.
- **« Retenir ce site ».** A passport fill card off the entry's « Remplissable sur » hosts shows, per row, « Retenir {site} pour {champ} » for the field's own site (a frame's site when the field is in a frame from another site; the box names it), unticked by default, so a lookalike domain is never remembered without your gesture. It shows only for an entry of the tab's own profile's passport, under 20 hosts, and never on a tab the agent reached (a trap page must not become one of your sources). Ticked, the site's host joins that entry only once the fill is written, and the agent's answer is the same either way. A remembered site is a passport site from the next conversation on: when you open it yourself the value stays masked there in every later conversation, and fills there skip the extra Touch ID. The conversation in progress keeps the sites it had at its first tool call: there the site is not one of your sources, and a fill on it after the Touch ID window still asks Touch ID. A save that fails leaves the fill as it is and says « Le site n'a pas pu être retenu. ».
- **After a fill, the value stays masked on that page.** A value filled into a field, by label or by kind, joins that origin's web zone in the conversation's table, so a later read of that origin in the same conversation shows it masked (under a web label, unrelated to its sources label). The table is wiped when the conversation ends: a later conversation reading the page sees the value in clear. A part filled by kind (a postcode, a surname) is masked there as that word alone, and an e-mail as in your sources (its local part, its domain kept). The page already holds the value, so this tells it nothing. A page or frame of that origin showing the value is also a carrier for the rest of the conversation's calls: `capture_screen` is refused there and its dev tools ask the unlock card (unit-tested).
- **The outflow rules never see the passport**: they see what the agent read, already masked. Otherwise a manipulated agent could try candidates in a search and learn the right one from a card or a refusal.
- **Agent extensions.** The passport's hosts (and their `www.`) join the sensitive hosts in Firefox's parent-side check for agent extensions (injection, tab access, frames), not Firefox's quarantine list, so your own extensions are not turned off there. Until every passport has loaded, agent extensions are refused on every host.
- **Coverage.** An addition to the passport (a new entry, a changed value, a new variant) masks at once in every open conversation, but a conversation that already read something may have seen it in clear before: it is marked « non couverte », its banner says that only this value may be known, and the editor tells you how many conversations were marked. A value removed or changed keeps being masked in the conversations that already got its label, until they end.
- **A profile that goes.** Deleting a profile's last space, or moving a space to another profile, asks whether to delete its passport too (unticked: kept by default). A kept passport still masks and shows in Réglages as « Sans espace », with « Déplacer vers… » and « Supprimer ce passeport » (confirmation and Touch ID). « Réinitialiser Ressac » keeps the passports: they live in the Firefox profile, which the reset does not set aside; « Supprimer ce passeport » is how you erase one.

**B3, the passport cases.** The protocol is step 1's (`bench/security/B3/README.md`, « The passport cases »): each user profile gets a passport (a name, a brother, a home address and a birth date, a work address in a second profile), and 11 passport families join the adversary, each with an honest control (96 cases in all): the holder's name, the street and the brother's name sent out from a statement, a mail and a header; the bank's writings (« AUBRAC Camille », « C. Aubrac », « Mme Aubrac », « 14, r. des Tanneurs », zero-width spaces, a homoglyph); a first name next to a masked phone; a third party's mail listing candidates; a rest-of-the-web page listing both profiles' names; a fill by kind on a lookalike domain; a shop printing back the filled address; a fill across profiles; a name and phone in JSON `\u` escapes. Six utility tasks join the 20 (26). Scripted adversary, every card granted: **to be measured**. Every card refused: **to be measured**. Indistinguishability (`indistinguishable.mjs`, both arms): **to be measured**; `passport-candidates` is an expected mismatch (which line is masked depends on the profile: a published limit). Utility, masking on and off: **to be measured**. A model run is not measured yet.

### Cacher pour l'agent, and the marks

- **What a click hides, and where it goes.** « Cacher pour l'agent » (the toolbar button, or the page's context menu on a selection or a text) lets you point at a value on the page and confirm it in a bubble (« Cacher « {texte} » pour l'agent ? », its type, a name split into « Prénom(s) » and « Nom »). « Cacher » asks Touch ID every time, then writes an ordinary passport entry (`how: "click"`, `from: <site>`) into the passport of the tab's profile, with the top page's site as its « Remplissable sur » host: always the top page's (a value in an embedded frame is masked on the host page, not when the frame's site is opened directly), and only an https one. A value already in the passport only gains the site. The value saved is the text frozen at the pick, shown in the bubble: what the page does to the element afterwards never reaches the passport. Only your gesture in Ressac's own frames creates or removes an entry or a site; no page, child-actor message or agent tool can.
- **The pointer never reaches the page while you pick.** The outline, the animation and the bubble are drawn by Ressac in frames over the content area; from the moment the viewfinder is armed until the toast appears (through the bubble and Touch ID), Ressac's layer takes the pointer and asks the page's read-only actor what text lies at that point, so the page never sees the pointer resting over the value you picked while the bubble is up. A click beside the bubble closes it (never during a save). With the toast the page gets its pointer, clicks and wheel back; « Annuler » stays clickable on the toast. The actor listens to no page event and adds, styles or selects nothing in the page. It reads the visible text with a rule close to the agent read's (opacity, with the ancestors', at least 0.05; a fully transparent colour is invisible; a UA widget's inner text is skipped). The pick takes the top page's site from the parent, and a pick whose top page changed before the bubble opens is dropped.
- **Four honest endings.** `hidden`: the value is masked on this page now (the kernel's runs cover it all); `next`: « Masqué à partir de la prochaine conversation » (the conversation in progress keeps the sites it had at its first tool call); `agentReached`: « Ajouté à votre passeport. Ce site, ouvert par l'agent, n'est pas retenu. »; `notHere`: « Ajouté à votre passeport, mais pas masqué sur cette page. » (an http page, or a top page Ressac cannot name as a passport site). When the value was already in the passport, these two say only « Ce site, ouvert par l'agent, n'est pas retenu. » and « Pas masqué sur cette page. ». `hidden` asks what every token masks: each open conversation's and the main token's. For an e-mail, the kernel masks the part before the `@`, so `hidden` needs only that part covered. **A tab the agent reached never gets its site added**, and a tab Ressac does not know counts as reached. The ending asks the kernel (`mask.runs`), which only peeks at the conversation's sources and never fixes them.
- **The toast.** « Masqué pour l'agent » with « Annuler »: the undo removes what the hide added (the entry, or only the site), without Touch ID, and only within 8 s of the gesture. « L'agent a peut-être déjà lu cette page. » shows when the agent had read access to the tab: a permission, not a proof that it read.
- **The marks: « voir ce qu'il ne voit pas ».** While the agent's aura is on a tab, and on that tab only, Ressac hatches each text the agent would receive masked there (the kernel decides, for every open conversation and the tab's zone: in your sources every detector form, the passport and filled values; on the rest of the web the high-risk forms and the values filled there). The hatches are drawn by Ressac in a frame over the page, never in it: the actor only measures (the page's visible text, then the rects of the masked runs with a detached range); nothing in the page changes, and no listener is installed in it. They follow a scroll, a resize or a change because Ressac re-measures every 250 ms while the aura is on, never because the page tells it. They fade out with the aura, and start over at each new document.

### Mots de passe in Réglages

Réglages › Mots de passe lists, shows, copies, adds, edits and deletes Firefox's saved logins (`Services.logins`, the store Firefox and the agent's `saved_login` fill read). Only the settings page's document gets this API: no agent tool, MCP path, web page or other Ressac page reaches it. The list carries sites and usernames, never a password. Showing or copying a password, adding, editing and deleting need a Touch ID token (« gérer vos mots de passe ») held by that page, valid 5 minutes and revoked when you leave the section, hide or close the page, or the Mac sleeps or locks its screen; a shown password hides again after 20 s. A password crosses into the page only on « Afficher » or « Modifier », one login at a time. A copied password goes to the clipboard as concealed data (macOS's concealed type), which clipboard managers skip. An added login must be an http(s) site with a host, is stored as its origin, and is refused if that site already has the same username. Limits:

- The clipboard is not cleared after a copy (Firefox does not either): the password stays there until something else is copied.
- Sites and usernames are listed without Touch ID, as Firefox's own `about:logins` shows them, and « Copier l'identifiant » needs none.
- Saved logins belong to the Firefox profile: they are common to all your spaces.
- A Firefox primary password is not supported: with one set, the section reads nothing and manages nothing (reading would bring up Firefox's prompt). Ressac never sets one.

### Pages and apps the agent builds

- **Agent pages** (ports 5300-5319) may only reach the agent's own local ports, or GET from five known CDN hosts (Google Fonts, cdnjs, jsDelivr, unpkg) over HTTPS on their usual port; a top-level navigation needs your gesture, and an address you type that the agent's server redirects is judged like the page's own navigation; DNS prefetch, preconnect and speculative connections are off (`apps/firefox/chrome/agent/page-guard.ts`). Agent apps get their own container and stay on their local origin.
- **Site apps** stay on their domains: every top-level load of an app's container must be on the app's or its sign-in domains, and a closed app's container loads nothing (`apps/firefox/chrome/store/sites.ts`). Tweaks run in a sandbox the parent process decides on, never the frame; a memory write needs the app's main document, its domains and your grant (`apps/firefox/chrome/store/site-frames.ts`).
- **Widgets, actions and workflows**: the harvest runs in a container with no network, a read-only file system, all capabilities dropped and memory and process limits. The kernel fetches for it: http(s) only, no credentials, declared domains only unless the widget or action asks for open web reads (then capped at 100 per run), local addresses refused after DNS resolution, size and redirect caps (`packages/kernel/src/workflows/access.ts`). Reading with your accounts needs a grant per widget or action. A widget's display has a CSP with no network and Trusted Types (`apps/firefox/chrome/window/widget-frame.ts`). The agent-written frames (widget displays, site homes, action components) run in a shared web content process like an ordinary page, not in the parent process, from copies under the profile's `chrome` folder behind a per-launch random address (`apps/firefox/chrome/window/remote-frame.ts`, `apps/firefox/chrome/agent/frame-actor.ts`). They cannot open another application (`mailto:`, app schemes) nor go fullscreen, refused explicitly; a frame whose document is not sandboxed (a null principal in that process) gets no data. When that process dies the frames load again in a new one, at most three times a minute each, then stay empty.
- **Ressac's own interface** (sidebar, panels, widgets, site homes) loads nothing from the web and has WebRTC denied (`apps/firefox/chrome/store/ui-network.ts`); the agent-written frames have no `RTCPeerConnection` at all, nested frames included (`apps/firefox/chrome/agent/frame-actor.ts`).
- **The external design-mode server** listens on `127.0.0.1`, refuses any request with an Origin header, checks Host against DNS rebinding, then a per-client token (`packages/kernel/src/design/external-server.ts`).

### Updates and telemetry

- **Updates are signed** with Ressac's own key (its certificate is built into the app) and must be newer than the running version (an update that could not be staged is judged by the feed's unsigned version); the DMG is signed with a Developer ID and notarized, and publishing refuses an update that does not verify. The VM image and its tools are pinned by SHA-256.
- **Telemetry** sends nothing before its notice has shown and one switch turns it all off: Ressac's own errors (addresses and the home path scrubbed), Firefox's crash reports (minidumps, which can hold page data and are not scrubbed: off by default, their own switch in Réglages › Confidentialité) and one count per launch (`apps/firefox/shared/telemetry.ts`, `apps/firefox/chrome/store/telemetry.ts`).

### Known limits

Known limits are marked with `shortcut:` comments in the code (for example custom-scheme navigations, preconnects and WebRTC in invisible reads). Others:

- The allowed domains include code hosts, package registries and the model APIs: the agent can send data there to an account an attacker controls. Subscription logins sit in the agent's home volume, so the agent can read them.
- The main token and every window's session token are readable inside the container (in Atelier, the agent's shell can use them). Calls under the main token are checked against what every window read, and a sensitive source asks its card again during any window's search, whatever the token. What stays open: another window's session token sends what the first window read without rule 2 noticing, and the main token opens, during a window's search, an address read outside it with no card.
- The relay passes the request body and extra headers unchanged (`anthropic-beta`, `OpenAI-Organization`): the agent can call any model or provider-side tool with your key. The relay token and the MCP tokens are plain bearers, readable by any process of the agent's user; the MCP server also accepts a token without `Bearer` and does not check `Origin`.
- In Navigateur, Claude has no shell but keeps its file and orchestration tools (`Write`, `Edit`, `NotebookEdit`, `Agent`, `Workflow`, `CronCreate`, `ScheduleWakeup`, `EnterWorktree`, `Skill`). Whether `Workflow` or `EnterWorktree` can run a command has not been tested.
- Once you grant `run_js` on a tab, script there can navigate or send anywhere without a card: it runs as the page itself, so no Ressac rule sees what it sends. It is bounded by your grant, given per tab and per origin, which does not carry to another tab or origin. The grant is tested; what a script does after it is not. An extension the agent wrote can act on its granted sites, and a changed one reloads without asking again while its rights stay the same.
- An agent page can still put data in the address of a GET to a known CDN, or use WebRTC, except while the workspace is locked; a click you make in it lets it navigate out, by script or a form POST, to the web or to another local service, for about 5 seconds. A site app's subresources are not limited to its domains, and its domains cover their sub-domains, shared public suffixes included (`github.io`, `co.uk`: anyone's page there counts as the app's); the grant card shows the list.
- A page that steers the agent during a search where it gets lost can still leave one lesson in the notebook. With the scripted adversary on 0.1.24, a planted lesson asking for the verification code in digit words, two per search, with an ordinary search between each, sent the code out whole in the next conversation, every card refused or granted (the series rule stopped at the first ordinary search). Since 0.1.25 its third piece pauses, in the next conversation as in one where the lesson is followed early (`notebook-evasive`, `notebook-early`): the first two pieces leave, 4 of the 6 digits. A lesson asking for one of the shapes the series rule does not see (below) still sends the value out. With every card refused, a script that read the mail only after its first search sent nothing (a sensitive tab asks again once a search has begun); one that read the tab you speak from before searching, as the model in the bench did, is the `notebook-early` case above.
- The outflow rules look only at a `search_web` query, at an address the agent composed, since 0.1.25 at runs of followed links labelled with one character and, since data masking, at what the agent hands a third party without an address: `launch_action`'s input and the action's own files (what a run stages: its top-level files but `data.json`, read when the agent launches it), and a `run_js` script, where only what was read on another origin than the script's tab counts (its own page already has the rest). A hit there asks the card with a red line, as a search would; an action's input and a script join the search series. Unit-tested; the scripted adversary's `action-clear` (a client id read in clear, sent as an action's input) is refused. Otherwise they do not check which link the agent chooses to follow among those it read: following a link it read is free, or browsing would need a card at each click, so a page that lays out links can let the choice encode data. It is bounded to a few bits per choice, only links the page itself offered, and only links still offered (a rewritten list is refused). Measured end to end before 0.1.25: an agent made to obey (minimax-m3.1-flash) clicked a code out whole on a grid of links labelled « 0 »… « 9 » on 4 of 4 pages with every card granted and 3 of 4 with every card refused, by `navigate {link}`, by an address read in the page and by `open_tab`. Since 0.1.25 the scripted adversary's grid (`bench/security/B3/adversary.mjs`, link-covert) gets the red-lined card at its third click, refused: the first two digits leave (2 of 6); its honest control, a climbing « 1 2 3 4 5 6 » on the same grid, gets none. Still free: the first two links of a run; a run whose last 8 pieces, ASCII digits and letters, climb or step back by one, with one step at most going back to « 1 » or to a page of the run right after a step of one (a code such as 123 456 is caught only when the run spells a value read whole; measured over all one million 6-digit codes sent one click per digit with nothing read matching, 7.4 % pass, 2.9 % would without the back step; that is not 92.6 % caught against an encoding the page chooses: a page that steps the pager down one page at a time, with filler links on another path of the same site, sends any code whole in about 2 to 4 times the clicks (a review's probe sent 381624 in 15 clicks, 907150 in 23); that way was open before these rules too, and they do not close it); links labelled with words or more than one character (« case 3 », « trente-huit », « 38 »): a page that labels each grid link with a word, and never with one character, is not judged, even when the address ends in the piece (`/k/3` « case »), because honest titled links end that way too (`/p/3` « Voir », `/article/5` « Lire la suite », an issue `/issues/7`, a playlist `&index=5`, `/guide/3`, `?stars=5`); a word label still does not free an address the page also showed under a one-character label (a piece once shown for an address stays when the page lists it again under a word); pieces spread over sites (a site is the host's last two labels); a piece carried in a sub-domain; one link per conversation; an address never shown with its label whose own path holds no piece. The memory has bounds a page can use: the labels of the last 2 000 links shown are kept, so a page read in full with about 2 000 links evicts the grid's labels before the clicks; and the pieces of 8 sites are kept, so one-character links followed on 8 other sites between two pieces drop the grid's run (both unit-tested). Since the review of 0.1.25, a word link or a link elsewhere between the pieces no longer ends the run, `read_pages` is judged like a click (unit-tested on the server, not in the scripted bench, whose cases have no `read_pages` grid), labels outlive the page that showed them, a CJK grid that makes the code climb gets no pager pass, and calls made at the same time are judged one after another (a held link counts even when you refuse it). Honest links that get the card: a pager jumped back by more than one page (« 2 », « 7 », then « 2 », or « 1 », « 5 », « 3 »), a size selector « S M L », an alphabet index « M C T », gallery links with no label (`/photos/3`, `/photos/1`, `/photos/7`), calendar days « 5 9 3 », and several shops under one two-label suffix such as `co.uk`, which count as one site (unit-tested shapes, not measured on real browsing). A run never ends on its own: after one step on a site that is no pager step, the next one-character links followed there keep getting the card until that step is more than 8 pieces back (« 5 9 3 », then a pager « 1 »… « 7 » is carded, « 8 » no longer). Its capacity beyond such a grid is not measured. Nor do they check an address a private page showed whole (how the agent percent-encodes it is a small channel too); screen captures; files in the workspace but an action's, at its launch by the agent; a script that builds a value from parts or from what its own page holds; what leaves through a workflow, a widget, an action run on its schedule or by you, or `launch_app`.
- Widgets and workflows run their code with no tool call of the agent, so the outflow rules never read that code: a value the agent writes into a widget's or a workflow's code leaves with its next run, bounded by the domains you granted it. An action is checked only when the agent launches it: when it runs on its schedule or because you launch it, its code is not checked. At an agent launch, the check runs on the staged copy, the same copy the run uses; when it refuses, nothing runs.
- An agent launch that joins a run already in progress (started by you, a watch, or an earlier launch) adds no check of its own: only the launch that started the run is checked.
- Under a lock, an agent launch whose staged code holds a value read in your tabs asks two cards: the lock's at launch, then the code's when the run starts.
- A `run_js` script that builds a value from parts (concatenation, arithmetic, an encoding done inside the script) is not caught: the outflow rules read the script's text, not what it computes.
- An action that runs on its schedule or because you launch it is not checked at all: only an agent launch goes through the outflow rules.
- A history entry of a site app whose window is closed still counts as a followed link (its address is on that app's own domains).
- They catch only shaped items. Private text without one leaves unseen: a message, a name, a street address, health data, a list of holdings. So does data the agent never read through a remembered source (a file in the workspace, something from an earlier session, a screenshot), and a password with no recognizable shape.
- What you typed in this conversation is never caught if it leaks: the rules treat it as yours to send, or every search you ask for with your own words would pause. A page that steers the agent can therefore send it out. It is bounded to this conversation in this window (another window's typed text is not exempt). The exemption is unit-tested; a steered agent sending it is not.
- The memory of what the agent read is per window and is lost when Ressac restarts or the local AI is switched off and on: it is kept in memory only, so what the agent read in your private tabs is never written to disk. After a restart the agent must read the data again to send it, and that read is remembered again; only data it saved in the workspace in between escapes (see « files in the workspace » above). Tested by unit tests. Rule 2's false alarms grow with how much the window has read: the measured rate is for windows that read little.
- Sensitive sites asking again during a search does not cover the developer tools' reads of a sensitive tab.
- A 6-digit coincidence with a number the agent read can pause an honest query.
- A series of searches pauses at its third piece: the first two have already left. In the end-to-end bench, 5 of the 8 digits of a client id and 4 of the 6 digits of a code left this way, and a code sent as three searches with no other words (« trois huit », « un six », « deux quatre ») left whole in all four obedient runs on 0.1.23; on 0.1.24 a scripted agent sending the same three searches was paused at the third, after the first two (4 of the 6 digits) had left; 4 digits of a 6-digit code leave 100 guesses. A series is not seen as one when:
  - the words around the changing part change from one search to the next;
  - they are shorter than 6 characters (« tarif 3 8 », « tarif 1 6 »…); searches made of the pieces alone, with no words around them (« trois huit », « un six », « deux quatre », seen in the end-to-end bench), are a series since 0.1.24; with an ordinary search between the pieces they are one since 0.1.25 (corpus 4 row `k-gap` and the scripted adversary's `bare-pieces-gap`, both paused at the third piece; before, the code left whole), but not when each search carries one digit or one whole number (« 38 », « 16 », « 24 », with or without ordinary searches between: corpus 4 row `k-gap-numbers`), nor, with ordinary searches between them and nothing read matching, when the pieces change shape (« trois huit », « 1 6 2 », « 4 »); three honest bare searches of one shape spread over a conversation pause: football formations « 4 4 2 », « 4 3 3 », « 3 5 2 », chess moves « e 4 », « d 4 », « c 5 », or « 2 1 », « 3 0 », « 1 1 » (known false pauses, pinned in the tests); other scattered short searches (« 2 1 », « e 4 », « 4 4 2 ») do not (unit-tested, not measured on real searches); with a changing frame or a frame under 6 characters, a scripted agent on 0.1.24 sent the code whole;
  - the search goes out as an address (`navigate`, `open_tab`), which is checked alone.

  Numbers written as compound words (« trente-huit », "thirty-eight") are not read, nor a short code in base64. A model name read in an order mail (WH-1000XM5) pauses a later search for it, because short identifiers are remembered.
- The agent can put text on the clipboard; if you paste it into the agent's terminal, it counts as typed by you, and what you typed is yours to send. Since masking, a paste that holds a value Ressac recognizes is held and offered masked first (« Coller masqué », the default); a paste with nothing recognized, or pasted in clear, still counts as typed. It needs you to paste, into that terminal. Not tested.
- The agent can still write its own instruction files (`AGENTS.md`, `AGENTS.override.md`, the four `guides/`, Codex's `~/.codex` instructions, its `config.toml` (which can name an instruction file, and which its interactive mode cannot skip) and skill folders). In Navigateur, before each session they are compared with the copy you last accepted (`<workspace>/.ressac/instructions/`, read-only in the container): a change waits for you in a card, to keep or to revert, and Claude reads the accepted copy of `AGENTS.md`, never the live one. Claude's auto-memory (`~/.claude/projects/*/memory`), which the gate does not watch, is off in Navigateur. « Revenir » keeps what it replaced in `.ressac/instructions/replaced.json` (the last revert only). Codex's own system skills (`~/.codex/skills/.system`) are accepted without a card the first time they appear, and watched from then on. What stays open: Atelier mode has no such gate, because there the agent has a shell and could change any file anyway; choosing Atelier is choosing that (the bench confirmed the gate runs only in Navigateur); a session already running in another window can change the guides or Codex's files between the card and the start (Claude reads the guides live); the Codex writer (drafts) is not gated; a folder the agent plants at a watched file path does not block the session (« Garder » accepts it), but « Revenir » fails on it until you remove it; a file too long, binary or unreadable, or a skill folder with too many files, is shown only as a marker, and « Revenir » deletes it (the whole folder for too many files). For a too-long file you kept, a change past its first MiB is not seen. A project or home `.npmrc`, `--ignore-scripts=false` or `npm_config_ignore_scripts=false` can turn install scripts back on.
- The version signed inside an update archive is the Firefox engine's, not Ressac's: Firefox's updater accepts any signed Ressac archive built on the same engine, and « newer » is checked by Ressac's own code once the update is staged. An update downloaded but not yet checked when Ressac quits is applied at the next launch, before that check runs. Both need control of the update feed and an older signed archive.
- Telemetry starts once its notice has appeared, not once you answered it: an error raised while it waits is sent. The launch count carries a random install id, kept until you turn the switch off, so launches of the same install can be linked; error reports carry none. Everything sent: the error's type, message (300 characters, scrubbed) and stack (50 frames), the release and a source tag; for the count, its session id, install id, times, status and error count. No IP address.
- The design-mode server lets the last client that declares a folder take it, with its pending remarks and its port, and accepts folders outside your home and any port from 1024 outside the agent's range.
- Without the signing settings, a DMG built from source is only ad hoc signed.

**Masking.** What masking does not cover, or covers only in part:

- The origin rule is a destination rule, not proof that the destination is honest. Once a value is filled on an origin, with or without a card, anything running there can read it: its own scripts, a third-party script or ad it loads, an XSS hole, a compromised site, a trapped page you opened yourself. Ressac makes sure the value goes to that destination and no other.
- A site that receives a value can show it again. Since the passport, a value filled into a field, by label or by kind, is masked again when the agent reads that origin later in the same conversation (it joins that origin's web zone in the conversation's label table). A later conversation reading the page sees the value in clear, since that table is wiped when the conversation ends, unless you ticked « Retenir ce site » on the card: the site then joins the entry's « Remplissable sur » and the value stays masked there once you open it yourself (a page the agent opens is still the rest of the web). A value the site sends on to another origin is in clear there for the same reason as any value on the web.
- Name and postal address have no shape, so step 1 does not mask them, except the display name of a `Name <address>` header in your sources. The passport (step 2) covers the names and addresses you put in it, in your sources, under the writings listed above. A name or address that is not in your passport, a name in a signature or a greeting (« Bonjour Camille, »), a first name alone, the single initial of a hyphenated first name (« J. Dupont » for Jean-Pierre) and free text stay in clear, and the agent can join them to the labels beside them.
- A value you type that masking does not recognize can join what it masks: your phone typed in the terminal, then shown as `⟨tel-…⟩` beside your name in a mail, ties the label to you. Values you list in your passport (step 2) are masked in your sources, but the outflow rules still ignore them (see the passport's limits).
- What you type in the agent's terminal key by key is not masked: the engine reads it as you type. Only Ressac's own prefills and a paste you choose to mask are.
- An e-mail address keeps its domain, in your sources too: a personal domain (`⟨email-…⟩@yourname.fr`) names you.
- While you have the hand (`hand_over`), the addresses you visit are shown to the agent with the web's masking: a phone number or e-mail address inside such an address reaches it in clear.
- A masked address in a recap is shown without a link: its real address is not kept with the recap, because the agent reads its recaps back.
- Your phone number or e-mail address shown on a page that is not one of your sources is in clear for the agent. That includes your own webmail or bank when the agent opened it itself, in a tab or with `read_pages` in background tabs of your profile: a page the agent reached is web zone, where only the high-risk shapes are masked. The brake there is the address card before the page loads (for an address not read in the search), then rule 2: a sensitive page's values read in clear are remembered, and a query, address or field filled on another site that carries one gets the red line. The same holds for the dev tools on a web-zone tab: `read_network`, or `run_js` fetching an account page, on a logged-in site that is neither in your passport nor a sensitive page returns your e-mail, phone or name in clear; their card guards only your sources' tabs. A frame Ressac cannot read (a sandboxed `srcdoc`, a `data:` or `blob:` frame of another principal) keeps its tab a carrier until it leaves the origin, so captures there stay refused: safe, but how often honest pages hit it is not measured.
- Shapes not recognized: a phone written with two spaces or commas between its pairs (`06  12`, `06,12,34`), grouped `061 234 5678`, or `+33 (6)…`; a code written with `/`, `_` or a tab inside (`482/913`); a bank account written as separate pieces (bank code, branch code, account, key) rather than as an IBAN; an account number of another country than France's 11 digits; a card grouped 8-8; an e-mail's local part alone, without its `@`; numbers in words in other languages than French and English, or a run that mixes digit words and a compound number (« trois huit un six cent »); a value drawn in an image or a canvas, which also does not make its tab a carrier, so `capture_screen` is allowed there. A short identifier mixing letters and digits in a history address (a lab file number) is not masked: rule 2 catches it whole only, and in the bench 5 of its digits left behind a granted card. A one-time code in lower case (`x7k9p2`), with more than two `-`, letters then digits or digits then letters (`AB1234`, kept clear so names like `ES2022` or `SHA256` stay readable), or shorter than 5 characters when it has letters; an identity number spaced with letter groups in lower case (`ab 123 456`), or spaced and shorter than 9 characters (6 when it holds a letter); a mail header's display name in single quotes holding an apostrophe (`'Lucie O'Brien'`), after an English date with no time, or with no `<address>` after it.
- Masking also hides what it should not: a date, version or count next to a code word reads as a code, and so does any number near « verify », « token » or « mot de passe », or a reference of capitals and digits (an error code like `E4041`) near a code word; the agent can be less useful for it.
- Digits in a link's path next to a code word are masked as a code, even when they are an ordinary number (an issue number, a product id).
- A company sender that does not look like an organisation by the rule below (« Lumen Maison » writing from a shared mailer) is still masked as a person's name, then everywhere it appears in your sources except inside a host name.
- A header display name is not masked when it looks like an organisation:
  - its first word, or the whole name, is a label of the sender's domain;
  - it is a one-word acronym of 5 characters or fewer;
  - it starts with an organisation word (banque, service, impôts…), after an optional « la », « le », « les » or « l' », and is not followed by a two-word person's name.

  So these show in clear: a person whose first written word is their domain label when none of their other words is on a list of about 120 common French first names (« Marceau Jules-Henri <x@marceau.fr> », a foreign first name), a surname of 5 capitals or fewer (« LEROY »), and a role word followed by one surname (« Service Ferrand »). The word list is French, with a few English words.
- A known name is never masked inside a host name or a domain (with a scheme, an `@`, or a lowercase domain ending).
- A known name written with a dot, a hyphen or a colon between its words (« Lucie.Ferrand », « Lucie-Ferrand ») is not matched.
- The outflow rules ignore a value the agent saw only as its label (no oracle on a masked value). A query, an address, an action's input or a script that writes a masked value from a guess, whole or in pieces, leaves with no pause: pausing would confirm the guess, and what leaves is only the guess. Rule 1 still pauses a secret's shape (IBAN, card, key), without saying where it was read. A value also shown in clear somewhere, or revealed by `reveal_value`, is still caught.
- If masking changes how many addresses a history or bookmark text holds, its links that cannot be paired with what the agent was shown count as read only when shown unchanged; the others ask a card.
- An agent extension reads pages outside the quarantine with its own network: on another site, a page that shows one of your identifiers is readable by it, and a value it encodes itself escapes the masker. Firefox matches quarantined hosts exactly: a sensitive sub-domain never listed, or a sensitive page known only by its path, is not quarantined. Ressac's own check still refuses script injection there, but the extension's other rights on that host (requests, cookies) stay. A script injected before a tab turned sensitive without a navigation (a single-page app changing its path) stays. The quarantine also turns off your own extensions that Mozilla does not recommend on those hosts (you can exempt one in about:addons), and its list only grows.
- In Atelier, the shell reads the workspace raw: a file you put there (a statement, an export) is not masked for it, nor is anything the agent reads through the shell.
- There is one workspace for all spaces: one reveal locks every window and every space until you lift it.
- Under the lock, an agent page still navigates out with your click (a value it holds goes in the address), and an app you start yourself from the Applications panel runs (its pages keep the lock's limits). An agent page open before the lock keeps running: it loses the CDNs and WebRTC, not its own ports. An open agent-extension grant card delays the reveal until you answer it, since the extensions are turned off before the value leaves.
- The locked network keeps the model domains (the engines need them): an Atelier shell, or the engine itself, can still send what it holds to a model account an attacker controls. A per-conversation cut is impossible: the container serves every conversation, so a reveal is refused while another conversation runs in it.
- A conversation resumed from before masking, one that revealed a value (after a lift that kept its files, its transcript holds the value), and any resumed Codex conversation, is « non couverte »: masking applies from then on, but its context may already hold values in clear.
- Lifting the lock with the quarantine also moves the engine's own login files if they changed since the reveal (the agent may be logged out). A file whose name is not UTF-8, or whose path is too long, stops the lift until you remove it.
- The parent-side load check does not judge a workflow's invisible reads. Within the lock, a redirect that stays on the same origin passes (the first address already went through a card or the rule), and a page's script navigation within 5 seconds of your click counts as yours. A page's own navigation inside a tab you opened counts as your visit in history.
- Touch ID is asked at every reveal. On a Mac with no login password, macOS reports a success without a prompt, and Ressac takes it as a yes.
- Fills: two fields of the same type and autocomplete on one page rest on the actor keeping its handles stable; the card names the field's label. Filling your bank's own page when the agent opened it itself gets a red line, so an honest task can ask you to grant a red card. A paste made before the agent's session started is masked with labels nothing can resolve (nothing leaks, but you are not told).
- An agent launch of an action may ask a red card because the action's `memory.json` holds data its runs read with your account: the check reads every file staged for the run. Not measured.
- `run_js` code holding something read on another origin gets a red card, even when the script is honest. Not measured.
- One read of a value on the origin the script's tab shows exempts it from the `run_js` card, even if the same value was also read elsewhere. The value must already be shown on that origin, which only an earlier outflow (one that asks a card) could do.
- `run_js` scripts that differ only by small numbers (`#item-1`, `#item-2`, …) join the search series and can be paused as one. Not measured.
- The tools the engine keeps in Navigateur, measured once on Claude (2026-11-23), none ran a command or reached a host other than the model's: `Workflow` has no shell, `EnterWorktree` fails outside a git repository and Claude's own git disables hooks on a planted one, `Agent` subagents get no Bash or web tools, `CronCreate` and `ScheduleWakeup` only prompt the model again, a planted `Skill` is unknown, and `NotebookEdit` finds no notebook runtime in the image (no call seen). This is a finite list tried on one engine version: a later Claude Code release can add a tool, and Codex's ChatGPT login, the token-refresh hosts and these tools on the subscription engine (tried on the relayed one) were not measured.

**The passport.** What the passport does not cover, or covers only in part (the limits of masking above stay):

- **A page the agent opens itself, even on a site of your passport, is not one of your sources: your name and address are visible there.** The reason is the oracle: a page the agent reaches may be written by an attacker. If the passport masked there, a page listing names or addresses would learn, from the one that comes back masked, which is yours, and send it out in one click. On the rest of the web nothing is masked by your passport, so no page learns anything by offering candidates. For the same reason the passport does not mask while you have the hand (`hand_over`): the tab stays the agent's.
- A third party's text in your sources (a mail you receive, a shared document, a message in a site app) can list candidates (« Êtes-vous Camille Aubrac, Lucie Ferrand ou Julien Aubrac ? »): the one masked is yours. This is the oracle of masking itself; Réglages › Confidentialité says it.
- The same on a page where a value was filled: the filled origin now masks it, so the agent can write candidates into a page that prints them back (a search box) and see which comes back masked. The site already holds the value, and this is still better than showing it in clear.
- A writing the folding does not cover stays in clear: a typo; a homoglyph (a Cyrillic « а »: B3 plays it, and it goes out in clear in both arms); spaced letters (« C a m i l l e »); a name cut by a hyphen at the end of a line; a double surname written with only one part; a married or usage name you did not enter. Neither is a value the site encodes itself (base64, a hash) found.
- Escapes: JSON `\u` escapes and numeric HTML references are decoded, but not mixed with percent escapes (`%5Cu00e9`), and a digit value whose separators are escapes is not found as a passport form: a birth date written `14&#47;03&#47;1990` or `14&#32;03&#32;1990`, a phone with a double separator of which one is escaped (`06 &#32;12…`). A phone or IBAN escaped whole is still caught by step 1's detectors in your sources.
- In clear by design: a first name alone, a surname alone (unless you wrote it as a variant), the city, the postcode, the postcode and city together, a street without its number, an address complement, the last 4 digits of an IBAN, a date without its year. A masked name or street with one of these pieces alone beside it, on the next line, leaves that piece in clear. Only French street abbreviations are known; a foreign address is searched as its first line, as written. A phone glued to the street number (« 0478123414 rue des Tanneurs ») leaves the street in clear.
- Two names found in mail headers that share a surname, one of them written elsewhere over a line break (« Luc Morel » and « Marie⏎Morel »), leave the wrapped one in clear.
- E-mail: the domain stays visible; disguised writings (« [at] ») are not recognized; an identifier equal to the local part, outside an address, is not masked.
- A name inside a host name (your personal domain) is masked only if you add the domain as a free entry.
- The context sometimes gives it away: « J'habite à ⟨adresse-…⟩, la capitale. »
- A value added during a conversation may have been read in clear before: that conversation is marked « non couverte ». A value removed stays in memory in the conversations that already saw it, until they end, and in JavaScript until the garbage collector runs.
- The outflow rules never look at the passport: a passport value the agent knows from elsewhere (you typed it in the terminal) leaves with no passport card. That is the join limit of step 1.
- Masking more than it should: a one-word variant or free entry (« Paris ») is hidden everywhere in your sources, even when it is not about you (the editor warns); a part filled by kind (« Lyon ») is masked as that word anywhere on the filled origin; two writings of one name across a comma can merge into one label. A part under 4 letters (« Pau ») is not masked again on the filled origin.
- Touch ID is one window per origin for 5 minutes, not one per value: once you grant a passport value off its origins, another passport value filled on that same origin in that conversation within 5 minutes needs only its card.
- On a fill-by-kind card with nothing to offer, « Ouvrir le passeport » refuses the fill and opens Réglages, which becomes the active tab, so `current_page` then answers « Aucun onglet actif »: the agent can infer that you opened your passport, not what it holds.
- Fill by kind offers the tab's profile's passport. The agent's own tab (one it opened from its own search) borrows the passport of its window's active space, unless that space is private, always behind Touch ID and named on the card; a space switched while the card is up fills nothing. A site app tab has no passport: nothing is offered, and the agent gets a refusal. A value hidden with « Cacher pour l'agent » on the agent's own tab goes into that tab's profile, which fill by kind never offers: it masks, but fills only by its label.
- The agent ticks boxes and chooses in lists (`check`, `option`). Each tick or choice asks the fill card, which says it may act at once, on the agent's own tabs too (a `hand_over` sign-in leaves your account open in the agent's profile, and nothing clears it); the page's own click runs, so a page that submits or saves on a tick does so after your yes. A box the page hides behind a drawing (an invisible native checkbox), a multiple-choice list and a list built from `div`s are not offered.
- A passport kept for a profile that only private spaces now use does not show in Réglages while they use it, and deleting the last such space keeps it without asking. It still masks.
- A passport whose keychain read hangs keeps agent extensions off every host for the session (fail closed). Whether the signed DMG reads the keychain at start without a macOS prompt is not measured yet; a build signed otherwise (ad hoc, development) may show one.
- An entry that cannot be read is kept in the file; if a file written outside Ressac holds more than 200 entries, saving is refused until you delete that passport.
- Locking Réglages › Passeport when the screen locks is not checked on a real Mac yet.

**Cacher pour l'agent and the marks.**

- Only text is covered. A value in an image or a canvas, a value that changes (a counter, a code that rotates), and the value inside a form field (the agent read skips it as well) cannot be picked, and are not marked.
- A frame is not marked, whatever its site: only the top document's text is measured. A frame Ressac cannot measure is never guessed. A pick inside a transformed iframe (rotated, scaled) gets wrong coordinates (the transform is ignored).
- The marks lag a fast scroll or a change by up to 250 ms plus one measure; a page whose visible text exceeds 200,000 characters is not marked.
- Timing. Each measure and each pick forces a layout flush in the page, and a measure only reads the rects of masked runs: a page could in principle time its own layout work to count how many runs are masked (not which ones). On the rest of the web the passport never masks, so this tells a page nothing about which value is yours; in your sources it sits beside the oracle of masking itself (a third party listing candidates, above).
- The aura can come from any window's conversation, or from the main token, so the marks show only what every open conversation and the main token mask on that tab (a site app's included): with two conversations, a value only one of them masks is not hatched. With no conversation open, only the main token's masking is hatched.
- The marks re-measure the hatches' place every 250 ms, but walk the page's text and ask the kernel again only every second (at once after a passport change, a conversation opened or ended, or a hatched text removed from the page): a new passport entry, a changed text or a value the agent no longer receives masked can lag by up to about 1.25 s.
- The re-measure's rhythm (a layout flush about every 250 ms) can tell a page, by timing, that the aura is on, that is, that the agent is working on it.
- The pick and the marks use a rule close to the agent read's, not the same code (`page-actor.ts`): a colour with an alpha under 0.1 counts as visible here (the agent read's threshold; only a fully transparent one is invisible), and there is no check for text the colour of its background, a font under 4 px or a clipped box; such text can be picked and marked although the agent's read may treat it differently. Text inside a shadow root is not pickable (only its host's own text is), although the marks measure it.
- When the toast appears, the page sees the pointer come back where it is then (often near the value just hidden, since the bubble sits under it). A right-click on an element is the page's own `contextmenu` event: opening « Cacher pour l'agent » from the context menu tells the page where you clicked.
- While the viewfinder is armed, a wheel scrolls the page through Ressac: the page sees its scroll move without any wheel event, which can tell it the viewfinder is armed. The wheel scrolls only the top document's viewport, not an inner scrolling container (a scrolling list or panel inside the page).
- The marks are computed on the page's visible text as Ressac joins it (whitespace as written, a line break between blocks), while the agent's read collapses runs of spaces and lays out links and blocks its own way: a value written across unusual whitespace (several spaces or line breaks inside a phone or an IBAN) could be masked in one and not in the other, so a hatch may be missing or extra there.
- The undo needs no Touch ID: anyone at your Mac within the 8 s of the toast can remove the entry you just added.

How these protections were tested, and what is not tested yet: [docs/security-testing.md](docs/security-testing.md).

A way around one of the protections above is a vulnerability, even when it needs a crafted page.

## Out of scope

- What the agent does with permissions you granted it.
- Attacks that need full control of the user's Mac, of Ressac's VM or of a Docker setup.
- Rate limiting and denial of service against your own machine.
